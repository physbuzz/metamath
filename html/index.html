Metamath Study Notes

Independently studying Metamath and its applications while staunchly saying "if I have to verify it in my head and not in a computer program then it's not math."

I mean seriously, you can't teach me about primitive symbols and then say "oh yeah but these represent different things so they're totally different." You just taught me to divorce the symbols from words, then staple words back on! But I'm getting ahead of myself.

Intro

This project started from reading through Norm Megill's public domain Metamath book, but grew into its own study project. My goals are:

  1. Build up to making formally verified metamathematical statements, inside Metamath. At the outset, it's very difficult to determine how ambitious to be. The best path to this appears to be doing this through set.mm, from which we use set theory tools to make metamathematical statements.
  2. Learn logic and metamathematics from a verifier-first perspective. "If it's not formally verified, it's folk knowledge, it's scattering bones and reading them"--is what I'd like to say, but in fact we still have to touch base with references. I haven't found any book that goes as far as I would like, perhaps they exist in the Lean- or Agda-sphere.
  3. Learn the history and terminology around important areas, while connecting to and citing literature. Thus, if I say a nonsequitur in conversation with logicians, I can at least say "oh, I was using the definition in Gaifman's 2002 student notes, what one are you using?" This helps us avoid (but doesn't entirely prevent) developing totally wacko ideas while completing independent studies.
  4. Deign to learn some of the important English language proofs, where we only our brains as proof checkers. This is how most of the literature works so it really can't be avoided. Also, sometimes, such as in peano.mm, the metamath database contains a lot of exposition in the form of prose assertions justifying the properties of the axioms.
  5. Perhaps learn some type theory (formalized in .mm) while we're at it.

The reason for my staunch "if it's not formally verified it doesn't exist" stance is not philosophy-first nor because I think it's pedagogically good. I simply don't understand the books. I can get an A in the coursework and repeat the English language proofs, but I am not sure that I'm not getting them wrong. I know that the verifier consisting of the examiner's brain finds the argument convincing, but I can't be sure that there's any sense to it at all. So I've been deeply deeply confused for a number of years and only now am I repairing that.

AI usage: I've found AI to be an absolutely horrible teacher, an OK problem set generator, and an absolutely amazing reference-finder, so I use it 0% for teaching and terminology, 60% problem set generations + human review (in the form of actually doing the problems), and 95% for finding references. For teaching, I think it gets stuck in a deep "intro to proofs" attractor. Dawg I'm a decade out from intro to proofs. Doesn't help that there's much less material with a verifier-first perspective. Tiny proof checkers:

  • Hirrolot, How to Implement Dependent Types in 80 Lines of Code (OCaml, Calculus of Constructions). An exceptionally small implementation of dependent type checking, including dependent function types, lambda abstraction, application, and beta reduction. Uses higher-order abstract syntax (HOAS) to simplify variable binding and substitution. A demonstration of how little code is needed for the mathematical core, although it is not a complete standalone proof-checking environment.

  • Andrej Bauer, How to Implement Dependent Type Theory I (OCaml, 92-line core). A particularly approachable tutorial implementing dependent type theory with a hierarchy of universes, dependent functions, substitution, normalization, and type inference. The complete program includes a parser and interactive interface. Parts II and III explore normalization by evaluation, de Bruijn indices, and explicit substitutions. Probably the best pedagogical starting point.

  • 45deg, Proofglyph (OCaml, Logical Framework). A small proof checker implementing the dependent lambda calculus underlying LF. Particularly interesting as a comparison with Metamath because different formal systems can be represented by declaring their judgments and inference rules. Uses de Bruijn indices and beta reduction, with a stack-oriented proof format and a separate readable frontend. Also has a browser-based demonstration.

  • John Harrison, HOL Light (OCaml, classical higher-order logic). A mature theorem prover built around a comparatively small kernel implementing primitive inference rules. Unlike the dependent type theory examples, HOL Light uses simple type theory and an LCF-style architecture. Worth examining because its small logical foundation supports a substantial library of formalized mathematics, although the complete system is considerably larger than the other examples.

  • Frank Pfenning et al., Twelf (Standard ML, Logical Framework). An established implementation of LF for representing deductive systems using dependent types. Includes proof checking, logic programming, and machinery for verifying metatheorems about encoded systems. Much larger than the minimal implementations above, but useful for seeing what a fully developed LF environment looks like.

Related paper:

  • Harper, Honsell, and Plotkin, A Framework for Defining Logics. The original presentation of LF, explaining how syntax, inference rules, and proofs of different formal systems can be represented using dependent type theory. Particularly relevant for understanding the mathematical ideas behind Proofglyph and Twelf.

Survey of proof checkers: - https://www.researchgate.net/publication/337829832_A_Survey_on_Theorem_Provers_in_Formal_Methods - Freek Wiedijk 2003, Comparing Mathematical Provers (PDF). Section 4.2, page 10, contains a table comparing 15 systems specifically against the de Bruijn criterion. Wiedijk identifies HOL, Coq, Otter/Ivy, Isabelle, Agda, PhoX, Metamath, Lego, and Omega as satisfying it. He also discusses the distinction between having a small kernel and having an independently checkable proof.
